# Runtime Calibration (launchd)

Real-runtime measurement of a live Whoosh'd deployment. The harness records
**measured** evidence only; it never estimates a performance claim and never
mutates runtime state.

## Why a launchd job

An agent sandbox cannot reach the GPU: `mlx.core` fails at
`metal::load_device` and the harness records that limitation honestly.
`launchd` runs outside such a sandbox, so a job it schedules *can* reach Metal
on the target host.

The harness itself does not need the GPU — it measures a deployment over
HTTP. The launchd path matters when the measurement must run with local
in-process GPU access, or when the operator wants the run to happen
unattended.

## Install

```bash
cp .local/launchd/com.resonant.whooshd-calibration.plist \
   ~/Library/LaunchAgents/com.resonant.whooshd-calibration.plist
launchctl load ~/Library/LaunchAgents/com.resonant.whooshd-calibration.plist
```

The job is **on-demand only** — `RunAtLoad` and `KeepAlive` are both false. It
does not run as a resident service.

## Run

```bash
launchctl start com.resonant.whooshd-calibration
tail -f /tmp/whooshd-calibration.err.log
```

Or run it directly (no launchd needed):

```bash
scripts/calibrate_runtime.sh
```

## Configuration

| Variable | Purpose | Default |
|---|---|---|
| `WHOOSHD_BASE_URL` | Broker base URL | `http://127.0.0.1:8000` |
| `WHOOSHD_UPSTREAM_URL` | Upstream runtime URL | `http://127.0.0.1:8082` |
| `WHOOSHD_UPSTREAM_MODEL` | Model id the upstream understands | none |
| `WHOOSHD_CALIBRATION_MODEL` | Broker model id | `local-chat` |
| `WHOOSHD_CALIBRATION_BANDS` | Concurrency bands | `1 2 3 4` |
| `WHOOSHD_CALIBRATION_REQUESTS` | Requests per band | `8` |
| `WHOOSHD_CALIBRATION_STAMP` | Report filename stamp | current UTC date |
| `WHOOSHD_CALIBRATION_OUT_DIR` | Report output directory | `docs/validation` |

## Output

Two files per run, under `docs/validation/`:

- `<stamp>-runtime-calibration.json` — the full evidence record
- `<stamp>-runtime-calibration.md` — a human-readable summary

## What is measured

| Metric | Source | Why it matters |
|---|---|---|
| `ttft_p50_ms` / `ttft_p95_ms` | client-side, first SSE content chunk | Latency floor for interactive tenants |
| `latency_p50_ms` / `latency_p95_ms` | client-side, request to terminal chunk | Total turn cost |
| `prefill_p50_ms` | upstream-reported `timings.prompt_ms` | The prefill tax that prefix reuse removes |
| `aggregate_tokens_per_second` | generated tokens / band wall-clock | Distinguishes max-working from recommended concurrency |
| `per_request_tokens_per_second` | mean per request | What a single tenant actually receives |
| `queue_latency_p50_ms` | lifecycle states | The smoothness metric |
| `swap_delta_pages` / `swap_in_delta_pages` | host `vm_stat` counters | Silent-thrash detector — critical on a fanless host |
| `cache_hit_ratio` | upstream-reported cached prompt tokens | The only legitimate basis for a cache claim |
| `leak_check` | `/runtime/admission` at rest | Lifecycle leak detection |

A measurement that could not be taken is reported as absent, never as zero.
Zero is a meaningful value for throughput and would misrepresent an
unavailable reading.

## Interpretation notes

- **The lane limit can be lower than the broker limit.** If the broker reports
  `effective_active_limit: 2` but the runtime lane accepts one request at a
  time, bands above 1 will show overload counts rather than real concurrency
  data. That is a measurement of the *deployment*, not a defect in the
  harness. Raise the lane limit deliberately, then re-measure.
- **Queue latency is only meaningful when the queue is enabled.** With the
  queue off, excess requests are shed as `429` rather than queued, and the
  queue-latency field stays empty.
- **Swap deltas are cumulative counters.** Only the delta across a band is
  meaningful; the absolute value is not.
- **Cache counters come from the upstream runtime**, which is the same process
  the broker forwards to, and therefore the same prompt cache. The broker's
  own response shape does not expose them.

## Privacy

Prompts are synthetic and generated by the harness. The report contains
counts, durations, and ratios only — never prompt text, generated text, token
identifiers, or KV state.
