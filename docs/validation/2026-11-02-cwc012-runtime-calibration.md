## 1. What was measured, and where it came from

The harness measures a **live deployment**, not a synthetic copy:

- Broker metrics (TTFT, latency, overload behaviour, lifecycle leak) are
  measured **through** Whoosh'd's HTTP surface.
- Runtime metrics (upstream prefill cost, prompt-cache hit counts) are read
  from the upstream runtime that Whoosh'd forwards to. It is the same server
  process and therefore the same prompt cache, so the numbers describe the
  deployment.

Prompts were synthetic and generated by the harness. The report contains
counts, durations, and ratios only — no prompt text, generated text, token
identifiers, or KV state.

## 2. Findings

### 2.1 The runtime already delivers prompt-prefix reuse — 95.6% hit ratio

The upstream MLX-VLM server reported **698 of 730 prompt tokens served from
cache** (hit ratio **0.956**) on a repeated 2 048-character prompt. Prefill
cost was **~275 ms** per request.

This is the most consequential result in this packet, and it is a
**measurement, not an inference**. Two consequences:

1. **Automatic prefix caching is working on this deployment.** Whoosh'd does
   not need to reimplement it to get prefix reuse.
2. **ThreadWake should not become a competing materializer.** The correct
   role for ThreadWake here is *observation and policy over observed cache
   behaviour* — which is the smaller, better-scoped system the project
   already describes. The "real backend materialization" roadmap item should
   be read in that light.

### 2.2 Effective concurrency is 1, not 2 — and the broker does not show it

The broker advertises `max_active_requests: 2` and
`/runtime/capacity` reports `effective_active_limit: 2`. In every band, one
of two concurrent requests was refused with **429**.

The binding constraint is the **lane**, not the broker:
`WHOOSHD_MLX_VLM_MAX_CONCURRENT_REQUESTS` defaults to **1** for vision
models (`whooshd/config.py:358-363`), and the MLX-VLM adapter enforces it
with its own semaphore (`whooshd/adapters/mlx_vlm.py:268-270`).

**Consequence for operators:** the broker's reported headroom can exceed what
the runtime will actually accept. There are **two independent ceilings** and
the lower one is real. Neither `/runtime/capacity` nor `/runtime/admission`
currently surfaces the lane's limit, so the advertised limit can mislead.

**Consequence for calibration:** concurrency bands above 1 **cannot be
exercised** on this deployment without first raising the lane limit. Bands
x2 and x4 in this packet are therefore not capacity measurements of the
12B — they are measurements of the lane's refusal behaviour.

### 2.3 The queue is disabled, so bursts are shed rather than queued

`/runtime/admission` reports `queue_enabled: false`. Excess concurrent
requests are refused with `429 runner_overloaded` instead of waiting.

For a multi-user chat deployment this is the smoothness failure mode: a
burst becomes visible errors rather than added latency. Enabling the bounded
queue is a deliberate operator decision with a real trade-off (latency versus
failure), not a default to change silently.

### 2.4 No lifecycle leaks, no swap thrash

`active_jobs` and `queue_depth` both returned to zero after the bands. Swap
**out** was zero throughout — the host did not thrash. Swap *in* pages
(686 then 225) reflect model pages being faulted in, which is expected and
decreasing as the model warms.

### Why the 12B band calibration is blocked rather than pending

The remaining work is not "run it later on the same setup". Raising
`WHOOSHD_MLX_VLM_MAX_CONCURRENT_REQUESTS` is an operator decision whose
safety depends on the very capacity evidence that is missing — a circular
dependency. It must be done deliberately on the target host, with the
launchd calibration runner, and with attention to the fanless-host throttling
question in §4.

### What would unblock it

1. Raise `WHOOSHD_MLX_VLM_MAX_CONCURRENT_REQUESTS` deliberately (start at 2).
2. Re-run the calibration through the launchd job so the measurement happens
   outside any agent sandbox.
3. Record the result as a new band set. Only then does a
   `CapacityProfile` with `recommended_active_concurrency > 1` become
   defensible.

**No 12B concurrency, throughput, or TTFT claim is made in this packet beyond
what was measured at concurrency 1.** E2B results are not presented as 12B
results.

## 4. Open question for the operator

The M4 MacBook Air is **fanless**. If a second node is added on that machine,
sustained 12B generation throttles *silently* — the router would keep sending
work to a node whose real capacity has collapsed, which is the opposite of
smooth load balancing. Running a smaller model on that node keeps it inside
its sustainable envelope.

This is a device-specific judgment and is recorded here as an open question,
not a decision.

---

## 5. Boundary note

This packet measures **one deployment** on **one host** with **one model**, at
**concurrency 1**. It is not a general throughput claim, not a comparison
between models or lanes, and not a capacity recommendation for the 12B. The
numbers describe this configuration and no other.

Nothing here claims a latency or throughput improvement: this is a baseline
measurement, not a before/after comparison.
